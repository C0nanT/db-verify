## Detalhes

### 1

**Problema.** Em `startWithPortRetry`, só o ramo de conflito de porta executa `rm -f` no nome fixo. Qualquer outro erro de `attempt` retorna na hora: falha de pull, erro do daemon, ctx cancelado no meio do `docker run -d`. O contrato de `Provision` em `engine.go` não diz o que acontece com o container quando há erro. Fora do core, o problema piora: Postgres, MySQL, MariaDB e Mongo retornam direto do `startWithPortRetry` sem `cont.Remove()` (`postgres.go:105-110`), enquanto o Redis limpa dentro do closure (`redis.go:141,146`). Além disso, `main.go:127-141` só instala `signal.Notify` *depois* que `Provision` retorna, e o ctx de `main.go:93` nunca é cancelado por SIGINT.

**Por que dói.** Um Ctrl+C durante um restore longo, caso reproduzível hoje, mata o processo e deixa `db-verify-<pid>` rodando com dados restaurados de um backup de produção. Cada engine nova decide a limpeza de novo, e as atuais já divergem.

**Evidência.**

```go
if !isPortConflict(err.Error()) {
    return 0, err
}
lastErr = err
_, _ = h.run()(ctx, "rm", "-f", name)
```

(`dockerhost.go:168-172`). A suíte só cobre o caminho feliz ("Close remove o container", `conformance_test.go:233-247`).

**Estratégia.** Um passo por PR:

1. Em `startWithPortRetry`, rodar `rm -f name` em todo caminho de falha. O comando é idempotente e o Redis já faz isso.
2. Documentar em `Provision` (`engine.go`): "Provision que devolve erro não deixa container para trás."
3. Criar um subteste de conformidade com ctx já cancelado que verifica `!containerExists`.
4. Em `main.go`, usar `signal.NotifyContext` antes de `Provision`. Esse passo fica fora do core; é só o ponto de apoio.

### 2

**Problema.** O cabeçalho de `relational.go` descreve 5 camadas (criação > publicação > atualização > qualquer data > PK) e afirma que "os nomes vêm de um lugar só". Mas `orderColumnTiers` guarda só as camadas 1 a 3. As camadas 4 e 5, o critério `byDate` e o desempate dentro de uma camada estão reimplementados por dialeto:

- **MySQL:** `columnPref`, `chooseOrderColumn` e `mysqlDateTypes`, em Go (`mysql.go:350-391`).
- **SQLite:** reaproveita a versão do MySQL construindo `mysqlColumn` (`sqlite.go:14,244,365`).
- **Postgres:** reescreve tudo como CASE em SQL (`postgres.go:311-314`).
- **Mongo:** achata as camadas 1 a 3 e não tem camada 4 (`mongo.go:367-368`).

O cabeçalho cita só Postgres e MySQL/MariaDB.

**Por que dói.** Mudar a heurística significa editar SQL em `postgres.go` e Go em `mysql.go`, e essa segunda edição altera o SQLite sem aviso. O comentário "um lugar só" dá uma confiança que não se sustenta. O caso concreto de desvio já está no código: numa tabela com `created_at` e `inserted_at`, MySQL e SQLite escolhem a primeira pela posição ordinal, enquanto o Postgres usa `DISTINCT ON … ORDER BY t.table_schema, t.table_name, c.pref NULLS LAST` (`postgres.go:338`), sem desempate. A coluna escolhida pode mudar de uma execução para outra.

**Evidência.** `relational.go:3-10` ("mas os nomes vêm de um lugar só"); `relational.go:17-24`, onde as camadas 1 a 3 são o array inteiro.

**Estratégia.** Um passo por PR:

1. Mover `columnPref` e `chooseOrderColumn` para `relational.go` sem mudar nada: tipo neutro `relColumn{Name, DataType}`, conjunto de tipos de data passado como parâmetro e `mysqlColumn` mantido como alias para os chamadores seguirem compilando.
2. Declarar `orderTierDateType = 4` com nome.
3. Corrigir o cabeçalho para listar todos os consumidores, incluindo SQLite e Mongo (parcial).
4. Criar um teste unitário para o empate na mesma camada.
5. Por último, e só então, adicionar `, c.ordinal_position` ao `ORDER BY` do Postgres. Isso muda comportamento, conforme a decisão 1.

### 3

**Problema.** `Available` descarta a saída e o `err` de `docker info`, e o mesmo acontece com o erro de `LookPath`. `dockerAvailable()` usa `context.Background()` e ignora o ctx que `Provision` recebe. Todas as 5 engines Docker chamam essa função.

**Por que dói.** Um daemon ou socket travado (modo de falha conhecido do Docker Desktop e do modo rootless) faz `docker info` bloquear para sempre, sem feedback. Quando falha, o operador não consegue distinguir "permission denied em /var/run/docker.sock" de daemon parado ou `DOCKER_HOST` errado. Além disso, o `requireDocker` dos testes pode pular a suíte inteira pelo motivo errado.

**Evidência.**

```go
if _, err := h.run()(ctx, "info"); err != nil {
    return fmt.Errorf("docker daemon não está acessível")
}
```

(`dockerhost.go:119-121`).

**Estratégia.** Incluir `strings.TrimSpace(string(out))` e `%w` na mensagem, e aplicar `context.WithTimeout(~10s)` em `dockerAvailable`. `TestDockerHost_Available` compara substrings, então continua passando. Num segundo passo, opcional, `dockerAvailable(ctx)` recebe o ctx de `Provision`.

### 4

**Problema.** `conformance_test.go` chama `requireDocker`, `collectionByName` e `containerExists`, e todos os `*_conformance_test.go` usam `uniqueName`. Esses helpers estão definidos em `docker_test.go`, que é o teste de fluxo completo **do Postgres** (módulo postgres).

**Por que dói.** Aposentar ou mover `TestFullFlow_Postgres` (boa parte dele duplica a conformidade) quebra a compilação da suíte genérica. Nada no nome do arquivo revela essa dependência.

**Evidência.** `conformance_test.go:82` (`requireDocker(t)`), `:167` (`collectionByName(collections, name)`), `:238` (`containerExists(hint.Name)`).

**Estratégia.** Mover os 4 helpers para `conformance_test.go` ou para um `docker_helpers_test.go` com a mesma tag `docker`. É uma movimentação pura, sem mudança de comportamento.

### 5

**Problema.** `Register` faz append sem checar nada, e `Engines()` devolve "na ordem de registro". Essa ordem é a dos `init()`, isto é, a ordem alfabética dos arquivos (mariadb, mongo, mysql, postgres, redis, sqlite). `detect.go:135` usa `>` estrito, então num empate vence a primeira engine. `Lookup` devolve o primeiro nome igual, e um `Name()` duplicado por copiar e colar entra sem erro.

**Por que dói.** Uma 7ª engine que reivindique `.sql` por extensão (50) empata com o MySQL, e o destino dos `.sql` passa a depender do nome do arquivo, sem erro de compilação nem teste vermelho. O mesmo vale para `conformanceFixtures`, indexado por nome.

**Evidência.** `engine.go:169-179`:

```go
func Register(e Engine) {
	registry = append(registry, e)
}
```

**Estratégia.** `Register` entra em pânico com nome duplicado. Criar `TestNoDetectTies` sobre as fixtures de `testdata/headers/`, que falha quando duas engines devolvem a mesma confiança máxima. Documentar a regra em `Register`. O comportamento atual se mantém, porque hoje não há empate (decisão 3).

### 6

**Problema.** Quando `containersUsingPorts` falha, `offerToFreePort` devolve `false, nil`, e quem chama reporta "nenhuma porta livre entre …". A leitura de stdin (`dockerhost.go:239`) também ignora o erro: EOF conta como "cancelar".

**Por que dói.** Numa falha de permissão ou num soluço do daemon, o operador recebe um diagnóstico errado sobre portas. O caso `ps` com erro não tem teste; `dockerhost_test.go:168-188` cobre só `ps` vazio.

**Evidência.**

```go
containers, err := h.containersUsingPorts(ctx, tried)
if err != nil || len(containers) == 0 {
	return false, nil
}
```

(`dockerhost.go:225-228`).

**Estratégia.** Separar os dois casos: com `err != nil`, devolver `fmt.Errorf("listar containers nas portas %v: %w", tried, err)`. Adicionar um teste `recRun` para esse caso (decisão 4).

### 7

**Problema.**

- `engine.go:37-38` cita `guessConfidence`, que não existe; a regra real é `detect.go:217` (`best.Confidence <= ConfidenceGuess`).
- `engine.go:16` repete num comentário os valores 100/50/10 ao lado das constantes de `:21-25`.
- `ProvisionOpts.ExactCounts` (`engine.go:53`) é preenchido por `main.go:125` e pelos testes, mas nenhuma engine lê o campo. O controle real é `Session.Collections(ctx, exact)`.

**Por que dói.** Quem lê o contrato procura um identificador inexistente e acha que `ExactCounts` configura o `Provision`. Mudar o comportamento de contagem por esse campo não surte efeito, e nada avisa.

**Evidência.** `engine.go:37-38` ("Confidence <= guessConfidence"); `engine.go:53` (`ExactCounts bool`); grep: nenhum leitor fora das atribuições.

**Estratégia.** Trocar o identificador para `ConfidenceGuess` e remover a lista duplicada de `:16`. Remover `ExactCounts` junto com as 3 atribuições (`main.go:125`, `conformance_test.go:97`, `docker_test.go:212`).

### 8

**Problema.** O contrato de `Recent` (`engine.go:159`) não fala em limite nem em ordem. Na prática o contrato é "no máximo 20 linhas, mais recentes primeiro", mas só a conformidade o impõe (`conformance_test.go:190`, `len(rs.Rows) > 20`), e o 20 está repetido como literal em `postgres.go:365,367`, `mysql.go:408,410`, `sqlite.go:205,207`, `mongo.go:419`, `redis.go:387,699` e `tui.go:428`. A verificação de ordem decrescente compara strings (`conformance_test.go:202-205`) e só vale para a coleção com coluna de data.

**Por que dói.** Mudar o limite significa caçar uns 9 literais, e nenhum erro de compilação aponta um esquecido. Os caminhos de fallback (PK, sem coluna, `_id` do Mongo) ficam fora do contrato testado.

**Evidência.** `engine.go:156-159`; `conformance_test.go:190-206`.

**Estratégia.** Criar `const RecentLimit = 20` com um doc comment em `Session.Recent` ("no máximo RecentLimit linhas; mais recentes primeiro quando a Collection tem ordem por data"). Apontar a conformidade para essa constante primeiro; as engines e a TUI migram quando alguém passar por elas.

### 9

**Problema.** `postgresPortWindow = 55432` e `freePort()` são regras exclusivas do Postgres dentro do módulo genérico de host. As outras engines guardam a porta padrão no próprio arquivo (`mysqlDefaultPort`, `redisDefaultPort`, `mongoDefaultPort`). `conformance_test.go:95-96` repete as 4 portas num comentário que vai envelhecer.

**Por que dói.** Quem adiciona ou muda a porta de uma engine precisa saber que só o Postgres passa pelo core. `port_flag_test.go` já precisa vigiar "55432" vazando para o help.

**Evidência.** `dockerhost.go:23` (`const postgresPortWindow = 55432`); `dockerhost.go:99-102` (`freePort()`).

**Estratégia.** Mover a constante para `postgres.go` como `pgDefaultPort`, fazer `postgres.go:95` chamar `freePortFrom(pgDefaultPort)` e apagar `freePort()`. Os chamadores são `postgres.go:95` e `docker_test.go:212,367`. Trocar o comentário da conformidade por uma referência às constantes.

**Sobre a decisão 7, uma alternativa melhor.** 55432 evita colidir com um Postgres local, e há um motivo ainda mais forte para mantê-lo: `psql` sem `-p` conecta em 5432, ou seja, no banco **do host**, e não no container de verificação. O operador pode então consultar ou alterar o banco errado sem perceber. O mesmo risco vale para `mysql` (3306), `redis-cli` (6379) e `mongosh` (27017). A regra consistente, portanto, é **todas as engines numa janela alta** (por exemplo 53306, 56379, 57017), e não o Postgres voltar a 5432. Isso muda comportamento e não é deste módulo decidir sozinho: cada engine teria que mudar a constante. Mover o 55432 para `postgres.go` já deixa o terreno pronto.

### 10

**Problema.** `DockerHost` foi feito com `Run`, `Listen` e `Stdin` injetáveis, mas as engines só o alcançam por wrappers de pacote presos ao global `defaultDockerHost`. Nenhum `Provision` recebe um host. Além disso, `DockerHost` cobre só portas e o check do daemon; o ciclo de vida do container é `exec.Command("docker", …)` cru em cada engine (7 em `postgres.go`, 7 em `mysql.go`, 8 em `redis.go` e 4 em `mongo.go`). As esperas de readiness são cópias: `postgres.go:183-208` e `mysql.go:239-265` são praticamente idênticas, e `mongo.go:250-272` já divergiu. O nome `db-verify-%d` se repete em 5 engines, e o prólogo de `Provision` (dockerAvailable → porta → retry → WaitReady → Remove em cada erro) é copiado à mão.

**Por que dói.**

- A lógica mais arriscada (timeout de readiness, a corrida do "servidor temporário", a limpeza em caso de falha, que é a linha 1) só se testa com `-tags docker` e containers reais.
- Uma correção no loop de espera precisa ser feita em 3 ou 4 lugares.
- Trocar para podman, `--context` ou um endereço de bind é editar `dockerhost.go` mais uns 26 pontos de chamada.
- Para uma 7ª engine não existe caminho documentado a seguir.

**Evidência.** `dockerhost.go:3-7` ("Engines Docker chamam daqui"); `dockerhost.go:93-112`:

```go
var defaultDockerHost = &DockerHost{}
...
func startWithPortRetry(ctx context.Context, name string, startPort int, attempt func(port int) error) (int, error) {
	return defaultDockerHost.StartWithPortRetry(ctx, name, startPort, attempt)
}
```

**Estratégia.** Direção definida pela decisão 2: `DockerHost` passa a ser o caminho único para a CLI Docker. Uma engine por PR:

1. Adicionar a `DockerHost`, sobre `h.run()`, os métodos `WaitReady(ctx, name, probeArgs, timeout)`, `Remove(name)` e `TailLogs(name)`, com testes `recRun` em `dockerhost_test.go`.
2. Migrar `pgContainer.WaitReady` e `mysqlContainer.WaitReady` primeiro. São cópias idênticas, então o comportamento se mantém.
3. Adicionar `Host *DockerHost` a `ProvisionOpts`; quando for nil, cai em `defaultDockerHost`.
4. Migrar o restante (run, cp, exec) engine por engine e extrair o prólogo comum.
5. Apagar os wrappers quando não houver mais chamadores.

A reescrita completa não é necessária; cada passo se sustenta sozinho.
